# ADR-012: Completion Criteria and Verifier Role

## Status
Accepted

- **Date:** 2026-08-26
- **Stage:** 13

## Context
In Run 11, the agent successfully implemented Milestone B of the plan and made a commit. The supervisor loop (ADR-008) saw the `.agent-harness/run_successful` marker and terminated the session, leaving Milestones C/D and remaining spec requirements incomplete. We need a mechanism to differentiate a milestone commit from a completed specification.

## Decision
We will decouple the "commit successful" event from the "spec complete" event by introducing a Verifier step in the supervisor loop.

1. **New Marker (`.agent-harness/spec_complete`):** 
   - The supervisor loop will now only terminate with success if `.agent-harness/spec_complete` exists. The existing `run_successful` marker will be repurposed simply to acknowledge a successful commit during an iteration.
2. **Verifier Role (`config/roles.yaml`):**
   - Create a `Verifier` role. Its allowed tools are strictly read-only plus execution: `read_constitution`, `read_specification`, `fs_read`, `fs_list`, and `run_tests`.
   - The Verifier's system prompt must instruct it to read the spec and the plan, run tests, and evaluate if all requirements are met. 
   - If met, the Verifier must write `.agent-harness/spec_complete` (via a dedicated new tool `mark_spec_complete` or an existing constrained write mechanism). 
   - If not met, the Verifier must output a bulleted list of missing requirements and failing tests.
3. **Supervisor Refactoring (`bin/run_agent.sh`):**
   - After a `SystemArchitect` iteration exits (whether it committed or timed out), the script must invoke Open Code using the `Verifier` role.
   - If the Verifier creates `spec_complete`, the loop exits successfully.
   - If the Verifier does not create the marker, its output (the list of missing items) is captured and passed back to the `SystemArchitect` in the next loop iteration via the `--continue` flag: `opencode run --continue "The Verifier reported the following incomplete items. Fix them and commit: \n<verifier_output>"`

## Implementation notes
- **`mark_spec_complete`** lives in `mcp_server/tools/git_tools.py` next to `write_marker`; it
  touches `.agent-harness/spec_complete`. It is an *optional* tool: the server registers it only
  when started with `--enable-tool mark_spec_complete`. `HarnessContext.optional_tools` carries the
  set; `git_tools.build_tools` appends the spec only when enabled. The implementer's MCP server is
  started WITHOUT the flag, so `mark_spec_complete` is not merely hidden in the client — it does not
  exist on the implementer's server. Only the Verifier's server enables it.
- **Two Open Code configs** are generated by `bin/gen_opencode_config.py` (extracted from the old
  inline generator): `opencode.json` (primary persona, server without the flag) and — implement
  phase only — `opencode.verifier.json` (Verifier persona, server with `--enable-tool
  mark_spec_complete`). Each run selects its config via `OPENCODE_CONFIG`.
- **Session pinning.** The Verifier runs as a *separate* Open Code session in the same directory, so
  after it runs it becomes "the last session". Resuming the implementer with a bare `--continue`
  would therefore resume the Verifier. The loop captures the implementer's session id
  (`opencode session list`, most-recent row) after its first run and resumes it explicitly with
  `--session <id>` (falling back to `--continue` only if the id could not be captured).
- **Loop.** Per iteration: run implementer (initial, or resume with the previous Verifier's feedback
  as the prompt), delete a stale `run_successful` first, then run the Verifier fresh. Success ⇔
  `spec_complete` exists (not `run_successful`). If the Verifier does not create it, its stdout
  (bounded to 4 KiB) becomes the next resume prompt: *"The Verifier reported the following incomplete
  items. Fix them and commit:\n<output>"*. Bounded by `MAX_RETRIES` (default 5); exit 3 on exhaustion.
- Plan phase and the generic (non-Open Code) `AGENT_CMD` path do **not** run a Verifier; their
  success marker stays `run_successful`.

## Alternatives considered
- **Verifier writes the marker with `fs_write`** — would require giving the Verifier a write tool and
  a write scope; a single-purpose `mark_spec_complete` keeps the Verifier otherwise read-only.
- **One config with both agents sharing an MCP server that always registers `mark_spec_complete`** —
  the implementer would be blocked only by a client-side tool toggle. Two servers make the exposure
  a real capability boundary, matching "expose ONLY to the Verifier".
- **Parse the implementer's spec adherence in the harness** — brittle; an LLM Verifier reading the
  spec and running the tests is the point.

## Self-critique
- The Verifier is the same local model as the implementer; it can be wrong in both directions
  (passing an incomplete spec, or failing a complete one). Its verdict is advisory to the loop, and
  a human still reviews the branch. A stronger/second model for verification is a future option.
- Session-id capture parses `opencode session list` output; a format change there would drop the
  loop back to `--continue`. The capture is best-effort with a logged fallback.
- The Verifier can loop-nudge a genuinely stuck implementer up to `MAX_RETRIES`; the ADR-010 stuck
  rule and a future `blocked` marker remain the escape hatch.
- `spec_complete` reflects the Verifier's judgement at one moment; a later commit does not re-clear it
  (the loop has already exited). Acceptable for a one-shot autonomous run.

## Consequences
- A single milestone commit no longer ends the run; the loop continues until an independent Verifier
  agrees every spec requirement is met and the tests pass, or attempts are exhausted.
- Verification is a reusable, capability-gated role; the pattern (a read-only agent that can set one
  marker) generalises to review/security gates.
- Autonomous implement runs are now implement→verify ping-pong, costing one extra Open Code session
  per iteration.
