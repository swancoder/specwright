# ADR-004: MCP Server Initialization

## Status
Accepted

- **Date:** 2026-08-25
- **Stage:** 4

## Context
The Agent Harness requires a standard communication interface to interact with the LLM. We need to implement the Model Context Protocol (MCP) server that will expose our tool stubs and the newly created Knowledge Graph engine to the agent.

## Decision
We will use the official Python `mcp` SDK to stand up the server using stdio transport.

1. **Dependency:** Add the official `mcp` package to `requirements.txt`.
2. **Entrypoint:** `mcp_server/main.py` will initialize the MCP server instance (`mcp.server.Server`) and use `mcp.server.stdio.stdio_server()` for communication. It must accept a `--target-dir` CLI argument.
3. **Tool Registration & Wiring:**
   - Expose the `query_temporal_coupling` tool by wiring it directly to the `DatabaseManager.query_coupled_files(target_path, min_jaccard)` method built in Stage 3. Return the results as a formatted string or JSON.
   - Register the other required tools (`fs_read`, `fs_apply_patch`, `run_tests`, `git_commit_feature`, `read_constitution`, `read_specification`). For now, their implementations must simply return a string: `"Not implemented yet"`. This allows the LLM to see their schemas without crashing the server.
4. **Tool Schemas:** Ensure strict Pydantic models are used for the arguments of all registered tools so the LLM receives accurate JSON schemas.

## Implementation notes
- Installed SDK is `mcp` 2.x. Its low-level `mcp.server.Server` takes `on_list_tools` /
  `on_call_tool` callbacks with `(ctx, params)` signatures instead of the 1.x decorators.
- `mcp_server/core/registry.py`: `ToolSpec` (name, description, Pydantic args model,
  handler) and `ToolRegistry` — transport-independent, so registration and dispatch are
  unit-testable without stdio. Args models use `extra="forbid"`; `call()` validates
  incoming arguments through the model before invoking the handler.
- `mcp_server/core/context.py`: `HarnessContext(target_dir, db)`; the graph DB defaults to
  `<target_dir>/.agent-harness/graph.db`, matching the indexer CLI.
- `query_temporal_coupling(filepath, threshold_percent)` calls
  `db.query_coupled_files(filepath, threshold_percent / 100)` and returns JSON.
- Each `mcp_server/tools/*.py` keeps its public function signatures and exposes
  `build_tools(ctx) -> list[ToolSpec]`; `main.build_registry(ctx)` aggregates them and
  `main.build_server(registry)` wraps the registry into `mcp.server.Server`.

## Alternatives considered
- **`mcp.server.mcpserver.MCPServer` / FastMCP-style decorators** — less code, but the ADR
  names the low-level `Server`, and the explicit registry keeps schemas and dispatch
  inspectable by tests.
- **Streamable HTTP transport** — unnecessary for a local LLM on the same machine; stdio
  keeps the harness sandboxed with no listening port.

## Self-critique
- `Tool` schemas are generated by `model_json_schema()`; Pydantic emits `title` keys and
  `$defs` that some clients render verbosely. Acceptable.
- The server opens the SQLite DB at startup; if the indexer has never run, the graph is
  empty and `query_temporal_coupling` returns `[]` rather than an error.
- Six tools are stubs; the LLM sees valid schemas but gets no behaviour yet.

## Consequences
- The harness can be launched as an MCP stdio server:
  `python3 -m mcp_server.main --target-dir <repo>`.
- Stage 5+ only needs to replace stub handlers; registration and schema plumbing are done.
- `bin/start_mcp.sh` can now wrap the entrypoint.
